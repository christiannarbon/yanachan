# Kubernetes

One command up, one command down. Aimed at a local cluster — minikube by
default.

```sh
make k8s-up      # cluster, image, secret, deploy, wait, tunnel
make k8s-down    # tunnel down, delete, wait for the namespace to go
```

`make k8s-up` is the whole sequence: it starts minikube if it is not running,
builds the image and loads it into the node, applies the secret, applies the dev
overlay, waits for the rollout, then opens a background port-forward and polls
`/api/health` until it answers. It prints the URL when it is ready.

## Targets

| Target | What it does |
| --- | --- |
| `make k8s-up` | everything, then a tunnel on <http://localhost:19080> |
| `make k8s-down` | removes the workloads and the PVC, waits for the namespace |
| `make k8s-status` | pods, PVC, service, and whether the tunnel is alive |
| `make k8s-logs` | follow the pod logs |
| `make k8s-tunnel` | restart the background port-forward |
| `make k8s-untunnel` | stop it |
| `make k8s-open` | port-forward in the foreground instead |
| `make k8s-restart` | roll the pod, to pick up a changed secret or image |
| `make k8s-load` | rebuild the image and push it into the node |
| `make k8s-validate` | render both overlays and schema-check them |

The background tunnel keeps its pid in `.k8s-portforward.pid` and its output in
`.k8s-portforward.log`, both at the repository root, so `k8s-down` and
`make down` can always find and stop it.

## Layout

```
k8s/base/              namespace, PVC, deployment, ClusterIP service
k8s/overlays/dev/      image :dev, laptop-sized resources
k8s/overlays/prod/     image :v1.0.0, 1Gi storage, secret managed out of band
```

`OVERLAY` picks which one every k8s target uses, defaulting to `dev`:

```sh
make k8s-up OVERLAY=prod
```

## The token in the cluster

`make k8s-secret` runs as part of `k8s-up`. If your gh CLI is logged in it asks
before doing anything:

```
  Forward your gh CLI token into the cluster? [y/N]
```

Answer no and the app comes up with no token, ready for the OAuth device flow.
Answer yes and the token is stored in the `yana-chan-4k` secret, which the pod
reads as `GH_TOKEN` — and the app still makes you approve it on the first screen
before it is used. Set `GH_TOKEN=...` in the environment to skip the prompt,
which is also what happens when there is no terminal attached.

Both secret keys — `gh-token` and `github-client-id` — are marked optional in
the Deployment, so the pod starts without a secret at all.

Changing the secret after the pod is running needs `make k8s-restart`.

For the **prod** overlay the secret is deliberately not generated by kustomize.
Create it out of band — a sealed secret, an external-secrets `ExternalSecret`,
or a one-off `kubectl create secret` — before applying.

## Why there is no Ingress

The service is deliberately ClusterIP. The pod holds a GitHub token and has no
login of its own, so reach it through the tunnel rather than exposing it.
This page describes the local-mode developer deployment; the Helm chart, when it
lands, runs [server mode](authentication.md#server-mode), which is built to be
exposed.

If you put it behind an authenticating proxy anyway, the hostname that proxy
uses has to be in `GHDASH_ALLOWED_HOSTS` or the app will refuse the request. See
[the security model](../tech/architecture/security.md).

## Pod hardening

Set in `k8s/base/deployment.yaml`, and worth keeping if you adapt it:

- `runAsNonRoot`, uid 10001, `seccompProfile: RuntimeDefault`
- `readOnlyRootFilesystem: true`, with an `emptyDir` on `/tmp`
- all capabilities dropped, no privilege escalation
- `automountServiceAccountToken: false` — the pod never talks to the Kubernetes
  API, so it has no business holding a service account token
- `strategy: Recreate` and one replica, because the state directory is a
  ReadWriteOnce volume that the old pod must release first

## State

On the PVC, mounted at `/data`. **`make k8s-down` deletes the PVC**, and with it
the stored session — you will sign in again next time.
